## 2. Key discoveries (hardware)

1. **The board has two USB-C ports with different roles:**
   - **ESP32 port** → CH343 USB-UART (`1a86:55d4`) → `/dev/ttyACM*` — flashing + serial monitor.
   - **Modem port** → SIM7600 USB (`1e0e:9001` QMI / `1e0e:9011` RNDIS) → `/dev/ttyUSB0-4` + network interface.
   The sketch talks to the modem over the **internal UART** (GPIO26/27); the modem USB port is only for PC-side AT/network testing.
2. **Pin map (from official LilyGO `utilities.h`, LILYGO_SIM7600X):**
   PWRKEY=4 (NPN-driven, GPIO HIGH = PWRKEY low), DTR=32 (hold LOW), STATUS=34 (HIGH = modem powered),
   battery ADC=35, solar ADC=36 (both via 100K/100K dividers → `analogReadMilliVolts() × 2`), LED=12.
3. **Battery rail behaviour on battery power:** comes up at boot (true voltage: 3.84 V cell #1, 3.97–4.04 V cell #2),
   then **collapses to a floating 0.28 V after 15 s (cell #1) / ~2 min (cell #2)**. The collapse coincided with a BT
   drop ⇒ likely a **brownout/reset of the whole board**. Root cause unknown (see §4).
4. The 0.28 V value = floating divider node (both ADCs read it when their rail is dead). A dead-rail reading is easy to
   recognize now.
5. The steady red LEDs near the SIM7600 are **charger-section LEDs** (CN3805): they indicate charging activity (VBUS
   present), not modem power. On battery they are legitimately off.
6. The battery "protection activation" pads (J1/J2, mentioned on the V1.2 schematic,
   `T-SIM7600X-schematic.pdf` page 1, Battery Interface section) are **not present/visible** on this board revision.
   Battery reseat was sufficient to (transiently) activate the path.

## 3. Key discoveries (software / tooling)

- **Flash command that works:**
  ```bash
  arduino-cli upload -p /dev/ttyACM1 --fqbn "esp32:esp32:esp32:UploadSpeed=921600,FlashSize=4M,PartitionScheme=huge_app" <sketch_dir>
  ```
- **BT SPP works great as the on-battery serial console.** Board advertises as `bike-01-debug`
  (MAC `XX:XX:XX:XX:XX:XX`, paired + trusted in bluetoothctl). Connect:
  ```python
  import socket
  s = socket.socket(socket.AF_BLUETOOTH, socket.SOCK_STREAM, socket.BTPROTO_RFCOMM)
  s.connect(('XX:XX:XX:XX:XX:XX', 1))   # SPP channel 1
  ```
- **Persistent logging:** `~/Arduino/sim7600/tracker.log` — both the BT reader and the MQTT listener append there
  (`[BT]` / `[MQTT]` tags). Watch with `tail -f ~/Arduino/sim7600/tracker.log`. (gitignored)
  The two listeners were started as background shells in the opencode session — they die with the session.
  Restart: see §6.
- **test.mosquitto.org became unreachable from the PC LAN** (TCP 1883 timeouts; EMQX/HiveMQ reachable).
  Bench builds now use `broker.emqx.io`. (The board publishes over cellular, which is a different network —
  it may still reach test.mosquitto.org, but for bench visibility we watch via emqx.)
- Arduino-ESP32 core 3.3.7; libs: TinyGSM 0.12.0 (has `poweroff()` → `AT+CPOF`), PubSubClient 2.8.0.

## 4. Open problems (in priority order)

1. **Modem does not power on from the battery rail.** Even while the rail measured 3.97–4.04 V for minutes,
   `testAT()` never succeeded. Facts to build on:
   - The modem **does** power on USB **only when no battery is installed** (Phase 1 conditions).
   - With battery installed, the modem has never answered AT, in any switch state, USB or battery.
   - ⇒ suspicion: the modem's VBAT node is fed through the charger/USB path and is **not** (or no longer)
     connected to the battery rail. Next steps:
     a. Run the flashed **passive-watch build** (build 23:22:39): on battery it never pulses PWRKEY for 90 s and logs
        `status=` / `batt=` — if the modem self-boots on the rail, AT will answer by itself.
     b. If not: **multimeter on the modem's VBAT** (SIM7600 pin or the nearest capacitor to it) with battery power vs
        USB power — find which node feeds it and where the break is.
2. **Rail collapse / brownout on battery** (15 s–2 min after boot, both cells). Suspects: DW01A/FS8205A protection
   tripping (e.g. from modem inrush — but it collapsed even while idle), bad switch/holder contact under thermal
   drift, or a board fault. Possibly related to #1 (inrush vs. protection). Instrument: the BT `[DBG] batt` stream.
3. **test.mosquitto.org unreachable from LAN** — use `broker.emqx.io` for bench; revisit for production (own VPS broker anyway).

## 6. How to resume

1. **Watch logs:** `tail -f ~/Arduino/sim7600/tracker.log`
2. **Restart the BT listener** (background):
   ```bash
   python3 -u -c "…BTPROTO_RFCOMM connect to XX:XX:XX:XX:XX:XX:1, append to tracker.log…" &
   ```
   (exact script in the session; keep the `buffering=1` file append + stdout mirror pattern)
3. **Restart the MQTT listener:** same pattern, `broker.emqx.io:1883`, topic `devices/bike-01/telemetry`.
4. **Flash:** USB-C into the **ESP32 port** → `/dev/ttyACM1`, command in §3.
5. **Serial monitor (USB):** pyserial on `/dev/ttyACM1` @115200, open with `dtr=False; rts=False`.
6. Before deployment, remove from `phase2-bt.ino`: `DEBUG_NO_SLEEP`, `BENCH_TEST_INTERVAL_S`,
   the forced-failure block, and switch the broker to the VPS one.
